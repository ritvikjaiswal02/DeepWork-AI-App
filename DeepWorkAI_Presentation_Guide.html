▸The 30-Second Pitch (memorize this)

If you say nothing else, say this.

“DeepWorkAI is a productivity app that helps knowledge workers reach and stay in a focus 'flow state'. It's a three-tier system: an Android app in Kotlin/Jetpack Compose runs focus timer sessions and tracks which apps distract you using Android's UsageStats API. A Ktor/Kotlin REST backend with a PostgreSQL database stores sessions, scores them, and handles auth with JWT. A Python AI layer adds two things: a machine-learning burnout-risk classifier (scikit-learn RandomForest) and an LLM productivity coach (Qwen-2.5-72B via HuggingFace). The backend calls the Python scripts when a session ends to compute burnout risk and personalized tips.”

1System Architecture (3-Tier Client–Server)

Classic layered architecture. The phone never talks to the database or Python directly — everything goes through the Ktor API. That's your headline design choice.

🗄️ PostgreSQL Database

③ AI LAYER — Python scripts (deepwork_ml)

scikit-learn · joblib · HuggingFace InferenceClient
burnout_model.pkl (RandomForest) LLM coach (Qwen-2.5-72B)
⚠ Key nuance to know (examiners love this): The Python layer is not a running web server. The README mentions Flask/FastAPI, but the real implementation in FocusRoutes.kt launches Python as a child process with ProcessBuilder, passes arguments on the command line, and reads the printed result back. So it's "backend shells out to a Python script," not "two servers talking over HTTP." Know this — it's the single most likely thing to get caught on.

6The "AI" Layer — exactly what it is

Be precise and honest here; this is where marks are won or lost. There are two distinct AI pieces.

① Burnout-Risk Classifier (true ML)

Model: RandomForestClassifier (100 trees), scikit-learn, saved as burnout_model.pkl.

Features (4): duration_min, hour_of_day, distraction_rate, focus_score.

Output: 0 = Low, 1 = Medium, 2 = High risk.

Trained on: 500 rows of synthetic random data (real DB used if ≥5 rows exist, else synthetic).

Labels: created by a rule (e.g. >120 min & score<60 → High).

② LLM Productivity Coach (generative AI)

Model: Qwen-2.5-72B-Instruct via HuggingFace InferenceClient (hosted, no local GPU).

Used for: distraction tips + the chat assistant.

Prompt: system role = "DeepWorkAI productivity coach" + your real stats as context.

Safety net: if the API key is missing or call fails, a rule-based fallback tip is returned, so the app never breaks.

⚠ The honest ML talking point: Because the model is trained on synthetic data whose labels come from a rule, the RandomForest is essentially learning to reproduce that rule — so reported accuracy is high (it's almost deterministic). The right way to frame it: "We built the full ML pipeline — feature engineering, training, serialization, and live inference from the backend. The synthetic data is a bootstrap; the same pipeline retrains on real user sessions once enough are collected (the code already prefers real DB data when available)." That's a strong, truthful answer.

8System-Design Choices & Trade-offs

3-tier separation

Phone → API → DB/Python. The client holds no DB credentials and no secrets. Trade-off: needs a running server; not offline-first.

Stateless JWT auth

Token carries email + userId; server stores no session. Trade-off: can't revoke a token before expiry (24h).

Exposed auto-migration

Tables created on startup — zero manual SQL. Trade-off: great for demo, but no versioned migrations for production.

Subprocess ML (ProcessBuilder)

Simplest possible integration — no second server to deploy. Trade-off: spawns a Python process per request (slow, not scalable). A real system would use a persistent FastAPI service.

Privacy-first framing

App-usage data is summarized to minutes-per-app, not full activity streams. Passwords BCrypt-hashed; Google users store no password.

LLM with rule fallback

Graceful degradation — the app gives advice even with no internet/API key. Good resilience story.

MVVM on Android

ViewModels isolate state from UI; survives config changes. Standard, testable.

Coroutines everywhere

Non-blocking DB (newSuspendedTransaction) + network. Keeps server & UI responsive.

  • 5. Start the tunnel (ngrok/cloudflared) and set the URL in the app's settings so the phone reaches the backend.
  • 6. Grant the app Usage Access permission in Android settings (needed for distraction tracking).
  • 7. Pre-create one account & a couple of past sessions so dashboards aren't empty.

The 6-step live flow

  1. Login — show Google or email login → "JWT issued, stored on device."
  2. Create a task in Task Planner → mark it "Deep."
  3. Start a focus session linked to that task → show ambient audio + timer.
  4. While it runs, open a distracting app (e.g., YouTube) for ~20s, come back.
  5. End the session → Summary screen shows focus score, the distracting app caught, and the burnout risk from the ML model.
  6. Open Flow Insights / Analytics → show the trend HUD + the LLM-generated tip.

11Pre-empt the Hard Questions (say these first, look confident)

  • "Is the Python a microservice?" → No, the backend invokes it as a subprocess via ProcessBuilder. Simple integration; a production version would use a persistent FastAPI service. (Own it before they catch it.)
  • "Is the ML real or just rules?" → Real scikit-learn RandomForest with a full train→serialize→infer pipeline; currently bootstrapped on synthetic data and retrains on real sessions as they accumulate.
  • "Is it secure?" → Passwords BCrypt-hashed, JWT auth, Google OAuth token verified server-side. Honest gap: not all session routes are token-protected yet.
  • "Does it scale?" → Architecture does (stateless API, Postgres). Bottleneck is per-request Python spawning — known, fixable with a long-running ML service.

12Top 30 Likely Questions — with answers

Grouped: architecture, backend/DB, ML/AI, Android, security, general viva.

Architecture & design

1. Describe your architecture in one sentence.

Three-tier client–server: a Kotlin/Compose Android client talks over REST/JSON to a Ktor backend, which persists to PostgreSQL and calls a Python ML/LLM layer for intelligence.

2. Why three separate tiers instead of one app?

Separation of concerns + security (the phone never holds DB credentials), and it lets each layer use the best tool — Compose for UI, Ktor for API, Python for ML.

3. How does the backend talk to the Python ML?

Via ProcessBuilder — it launches the Python script as a child process, passes inputs as command-line args, and reads the printed output. Not HTTP.

4. Why not a Flask/FastAPI server for ML?

Simplicity for the project scope — one less server to run/deploy. Trade-off is a new process per request; I'd switch to a persistent FastAPI service to scale.

5. What are the main trade-offs in your design?

Server-dependent (not offline-first); 24h non-revocable JWTs; per-request Python spawning; auto-migrations instead of versioned ones. All acceptable for the scope, each has a clear upgrade path.

6. How would you deploy this for real?

Containerize the Ktor app, host on a cloud VM/managed service, use managed PostgreSQL, run the ML as a separate FastAPI container, and front everything with HTTPS instead of an ngrok tunnel.

Backend & database

7. Why Ktor over Spring Boot?

Lightweight, Kotlin-native, coroutine-based — fast startup and less boilerplate for a focused REST API.

8. What is Exposed and why use it?

A Kotlin SQL framework/ORM. It gives type-safe queries (no raw SQL strings) and auto-creates tables from the Table objects at startup.

9. Walk me through your database schema.

Seven tables centered on users; focus_sessions records each run, distraction_logs the apps used, plus tasks, wellness_logs, session_history, daily_analytics, cognitive_challenges — all linked by user_id.

10. How is the focus score calculated?

Start at 100, subtract 5 per distraction (clamped 0–100), then multiply by completion ratio (actual time ÷ target time, capped at 1) so quitting early lowers the score.

11. What happens, step by step, when a session ends?

Backend computes the score, calls the ML script for burnout risk, then writes to focus_sessions, session_history, daily_analytics, and distraction_logs, and returns the session + risk to the phone.

12. Are database calls blocking?

No — they run inside newSuspendedTransaction on the IO dispatcher, so they're non-blocking coroutines.

13. Do you use foreign keys?

Honestly, no enforced FKs — relationships are by shared user_id convention. Fine for this scope; I'd add constraints for production integrity.

14. How do you handle errors in routes?

Each route wraps logic in try/catch and returns appropriate HTTP codes (400/401/404/500) with a message instead of crashing.

Machine learning & AI

15. What ML model do you use and why?

A RandomForestClassifier — robust, handles non-linear feature interactions, fast inference, and interpretable for a small feature set.

16. What features does the burnout model use?

Four: session duration, hour of day, distraction rate (distractions ÷ duration), and focus score.

17. How was it trained, and on what data?

A full pipeline in train_model.py: it pulls real sessions from Postgres if available, otherwise bootstraps on 500 synthetic rows; labels come from a rule, then RandomForest fits and is saved with joblib.

18. Isn't training on synthetic data a weakness?

It's a cold-start bootstrap — the pipeline already prefers real DB data once ≥5 sessions exist, so the same code retrains on genuine user behavior over time.

19. What's the difference between your ML model and your LLM?

The RandomForest is a small predictive classifier (burnout risk 0/1/2). The LLM (Qwen-2.5-72B) is a hosted generative model that writes natural-language coaching tips and chat replies.

20. What if the LLM/API is down?

There's a rule-based fallback that returns a sensible tip, so the feature degrades gracefully and never errors out to the user.

21. Why Qwen via HuggingFace instead of OpenAI/local model?

Hosted inference needs no local GPU and the HuggingFace free tier kept it zero-cost; the code is model-agnostic, so swapping models is one line.

22. How does the model output reach the user?

Python prints 0/1/2; the backend maps it to Low/Medium/High, saves it, and sends it in the session-end response, which the summary screen displays.

Android client

23. Why Jetpack Compose?

Declarative, less boilerplate than XML layouts, and it made the custom animated HUD/charts (drawn on Canvas) much easier.

24. What architecture pattern on Android?

MVVM — ViewModels hold screen state and call the network services, keeping Composables stateless and surviving config changes.

25. How do you detect which apps distracted the user?

Android's UsageStatsManager. At session end we query foreground events in the session window and compute per-app minutes — requires the user to grant Usage Access permission.

26. Does that violate privacy?

It's opt-in (explicit OS permission), data is summarized to minutes-per-app rather than raw activity, and it's tied to the user's own account — consistent with the privacy-first framing.

27. How does the app communicate with the backend?

Ktor HTTP client over coroutines, sending/receiving JSON; the base URL is configurable so it can point at the local tunnel.

Security & general viva

28. How is authentication handled?

Email/password (BCrypt-hashed) or Google sign-in; on success the server issues a JWT (HMAC256, 24h) carrying email + userId, which the client sends on protected routes.

29. Any security weaknesses you'd fix?

Yes — not every session route is JWT-protected yet (start/end take userId in the body), and secrets/paths are read from env but default to local values. I'd protect all routes and externalize all config.

30. If you had two more weeks, what would you add?

Protect all endpoints, move ML to a persistent FastAPI service, add real foreign keys + DB migrations, retrain the model on accumulated real sessions, write automated tests, and deploy to the cloud with HTTPS.
